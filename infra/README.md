# Инфраструктура

PostgreSQL поднимается вместе с остальными сервисами через `docker compose` из корня репозитория.
SQL-файлы из [db/](db/) выполняются по алфавиту **только при первом запуске** на пустом томе.

После изменения схемы базу нужно пересоздать, данные при этом удаляются:

```sh
docker compose down -v
docker compose up --build -d --wait
```

Подключение снаружи: `postgres://advertising:advertising@127.0.0.1:5432/advertising`.
Порт и пароль меняются переменными `DB_PORT` и `DB_PASSWORD`.

## Модель данных

![Модель данных](schema.png)

| Таблица | Назначение |
|---|---|
| `users` | Агенты и админы. Вход по логину, логин хранится в нижнем регистре. Необязательное отображаемое имя. |
| `session` | Вошедшие пользователи. В cookie лежит токен, в базе его хеш. Срок жизни фиксированный. Выход удаляет запись. |
| `channel` | Площадка: название, описание для агента, включена ли, текущая версия настроек. |
| `channel_version` | Неизменяемая версия настроек площадки: промпт, чеклист, лимиты. Каждое сохранение создаёт новую версию. |
| `listing` | Объявление: данные объекта от фронта, результат последней удачной генерации, состояние генерации. |
| `photo` | Фото объявления: файл и превью в хранилище, метаданные, оценка нейросетью. |
| `file_cleanup` | Ключи файлов удалённых фото, которые фоновая задача должна стереть из хранилища. |

Все идентификаторы — UUID v7. Полный список требований — в [docs/requirements.md](../docs/requirements.md).

## Договорённости

**Пользователи.** Регистрация создаёт только агентов. Админа назначают вручную в базе. Блокировки нет: доступ закрывается удалением пользователя вместе с его данными.

**Генерация.** Отдельной таблицы генераций нет, состояние хранится в объявлении.
- Во время генерации объявление заблокировано: бэкенд отклоняет правку данных, загрузку и удаление фото, удаление объявления.
- Запуск атомарный: статус меняется на `generating`, только если генерация ещё не идёт. Время старта пишется в `generation_started_at`.
- Генерация дольше 50 секунд сбрасывается в `failed`. Поздний ответ такой генерации отбрасывается: результат записывается, только если статус всё ещё `generating` и время старта совпадает.
- `result` перезаписывается только при успешной генерации. При сбое в нём остаётся прошлый результат, а код ошибки пишется в `generation_error`.
- Изменение данных объекта возвращает статус `draft`, но `result` не стирает. Статус `draft` вместе с непустым `result` означает «результат устарел».
- Формат `result` ещё обсуждается. В любом случае он хранит, на каких версиях площадок получен.

**Одновременное редактирование.** `listing.version` растёт при каждом сохранении. Сохранение со старой версией отклоняется, и фронт показывает экран конфликта. У площадок ту же роль играет номер текущей версии.

**Данные объекта.** Формат `listing.data` задаёт контракт с фронтом, бэкенд передаёт его в генерацию целиком. В `data` хранятся и дополнительные указания агента для генерации. `updated_at` меняют только действия агента: правка данных, загрузка и удаление фото.

**Фото.** Принимаются только JPEG и PNG. После загрузки готовится превью и нейросеть оценивает фото: годность (`quality`), обоснование (`quality_reason`), что на фото (`scene`). Пока это не готово, статус `processing`; при сбое — `failed` с кодом ошибки в `error`. Такое фото агент удаляет и загружает заново. Генерация запускается, только когда все фото объявления в статусе `ready`. Порядок фото — порядок загрузки, рекомендованный порядок хранится только в результате генерации.

**Площадки.** Площадки не удаляются, только выключаются. У площадки всегда есть текущая версия. Текущей можно сделать любую версию, в том числе старую — это откат (в интерфейсе после демо). Версии не удаляются: на них ссылаются результаты генерации. Лимиты считаются в символах, лишнее бэкенд обрезает. Общий системный промпт живёт в коде бэкенда и не версионируется.

**Удаление.** Объявление удаляется сразу, вместе с фото. Ключи оригинала и превью триггер складывает в `file_cleanup`, оттуда их забирает фоновая задача. Файлы, загруженные в хранилище без записи в базе, на демо допускаются.

## Начальные данные

[002_seed.sql](db/002_seed.sql) создаёт площадки Авито, ЦИАН и Telegram с черновыми промптами, чеклистами и лимитами. Пользователей в начальных данных нет: формат хеша пароля зависит от бэкенда.
