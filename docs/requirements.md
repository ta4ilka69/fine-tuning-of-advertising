# Требования к продукту (со стороны разработки)

Требования, которые следуют из модели данных и принятых технических решений. Это не пользовательские сценарии, а правила, которые обязаны соблюдать бэкенд, фронтенд и база.

Статус: черновик, формируется при разборе схемы БД. Открытые вопросы — в конце.

## Общие принципы

- **О-1.** Названия полей в БД главные. Контракт API и код бэкенда следуют им или явно сопоставляют.
- **О-2.** Все идентификаторы — UUID v7.

## Пользователи и сессии

- **П-1.** Вход по логину: 3–32 символа, только `A-Z a-z 0-9 _ . -`. Логин уникален без учёта регистра и хранится в нижнем регистре.
- **П-2.** Пароль: 12–128 символов, не обрезается и не нормализуется. В БД хранится только хеш, формат хеша выбирает бэкенд.
- **П-3.** Роли: `agent` и `admin`. Регистрация создаёт только агентов. Админа назначают вручную в БД, автоматического создания нет.
- **П-8.** У пользователя есть необязательное отображаемое имя `name`. Если его нет, в интерфейсе показывается логин.
- **П-9.** Блокировки пользователя нет: доступ закрывается только удалением, и данные удаляются вместе с ним.
- **П-4.** Сессия: в cookie случайный токен, в БД только его хеш. Выход удаляет запись сессии.
- **П-5.** Срок жизни сессии фиксированный и отсчитывается от момента входа. Скользящее продление пока не делаем.
- **П-6.** Просроченные сессии периодически удаляются.
- **П-7.** Роль в сессии не хранится, она читается из пользователя. Смена роли действует сразу.

## Объявления

- **Л-1.** Объявление принадлежит одному пользователю.
- **Л-2.** Данные объекта хранятся одним JSON-документом в поле `data`. Его структуру задаёт контракт с фронтендом.
- **Л-4.** Дополнительные указания агента для генерации хранятся в `data` вместе с остальными данными и учитываются при каждой генерации.
- **Л-5.** `updated_at` меняется только от действий агента: правка данных, загрузка и удаление фото. Завершение генерации его не меняет. Список объявлений сортируется по `updated_at`.
- **Л-3.** Защита от одновременного редактирования: у объявления есть версия, она растёт при каждом сохранении. Сохранение со старой версией отклоняется (`409`). К демо достаточно одного экрана «Объявление изменилось в другом окне, обновите страницу».

## Генерация

- **Г-1.** Генерация асинхронная и выполняется в фоне. Отдельной сущности «генерация» нет: состояние хранится в объявлении.
- **Г-2.** На одно объявление одновременно идёт не больше одной генерации. Запуск атомарный: статус меняется на `generating`, только если генерация ещё не идёт.
- **Г-3.** Во время генерации объявление заблокировано. Блокировку проверяет **бэкенд**: отклоняются правка данных, загрузка и удаление фото, удаление объявления.
- **Г-4.** Время старта генерации сохраняется. Генерация, которая идёт дольше 50 секунд, сбрасывается в `failed`, блокировка снимается.
- **Г-8.** Завершение генерации записывается только если объявление всё ещё в статусе `generating` и время старта совпадает с запуском. Поздний ответ сброшенной генерации отбрасывается и не перетирает новое состояние.
- **Г-9.** Ошибка генерации хранится кодом, как у фото (Ф-8).
- **Г-5.** Результат перезаписывается только при успешной генерации. Ошибка последней генерации хранится отдельно от результата, прошлый результат при сбое сохраняется.
- **Г-6.** Правка данных возвращает статус `draft` и не стирает результат. `draft` вместе с непустым результатом означает «результат устарел».
- **Г-7.** Результат хранит, на каких версиях площадок он получен.

## Фото

- **Ф-1.** У фото хранятся имя файла, MIME-тип, размер, позиция, статус, ключ файла и ключ превью в хранилище, ошибка обработки.
- **Ф-2.** Статус `processing` покрывает подготовку превью и AI-оценку. `ready` — оба этапа завершены, `failed` — любой из них упал.
- **Ф-3.** Генерация запускается, только когда все фото объявления в статусе `ready`.
- **Ф-4.** AI-оценка фото — внутренние данные для генерации: `quality` (`unfit` / `needs_fix` / `good`), `quality_reason` (почему такая оценка), `scene` (что на фото). Фото не может быть `ready` без всех трёх полей.
- **Ф-5.** Агент не меняет порядок фото вручную. Фото показываются в порядке загрузки, отдельного поля позиции нет: сортировка по `id` (UUID v7 растёт со временем). Рекомендованный порядок хранится только в результате генерации.
- **Ф-6.** Фото в статусе `failed` не обрабатывается повторно: агент удаляет его и загружает заново.
- **Ф-7.** На демо принимаются только JPEG и PNG. HEIC не поддерживается.
- **Ф-8.** Ошибка обработки фото хранится кодом (`too_large`, `unsupported_format`, `ai_failed` и т. п.). Текст для пользователя бэкенд собирает по коду.

## Площадки

- **К-1.** У площадки есть уникальное название и описание-подсказка для агента. Машинного кода нет: площадки — это данные, и код не должен вести себя по-разному в зависимости от конкретной площадки. Всё поведение задаётся промптом, чек-листом и лимитами.
- **К-2.** Админ создаёт площадки, включает и выключает их. Выключенная площадка не предлагается агентам, старые результаты по ней сохраняются.
- **К-9.** Каждое сохранение настроек создаёт новую версию, даже если ничего не изменилось. Пропуск одинаковых версий — позже.
- **К-10.** Автор версии не хранится.
- **К-11.** Лимиты длины считаются в символах Unicode. Бэкенд сам проверяет длину ответа модели и обрезает то, что превышает лимит. Резать лучше по границе предложения или слова, а не посреди слова.
- **К-12.** Общий системный промпт живёт в коде бэкенда и не версионируется: он меняется вместе с релизом. Версия площадки фиксирует только её собственные настройки.
- **К-6.** Площадки не удаляются, только выключаются: на их версии ссылаются результаты.
- **К-7.** У площадки всегда есть действующая версия настроек. Площадка и её первая версия создаются в одной транзакции.
- **К-8.** Название, описание и признак включения не версионируются: они не влияют на результат генерации.
- **К-3.** Настройки площадки (промпт, чек-лист, лимиты) версионируются. Версия неизменяема, каждое сохранение создаёт новую.
- **К-4.** Чек-лист — упорядоченный список строк. Результат проверки ссылается на правила по порядку внутри версии.
- **К-5.** Откат к старой версии — после демо.

## Хранилище файлов

- **Х-1.** Файлы хранятся в S3-совместимом хранилище.
- **Х-2.** Файлы удаляются асинхронно через очередь `file_cleanup`. При удалении фото ключи оригинала и превью попадают в очередь в той же транзакции. Очередь заполняет триггер, поэтому каскадные удаления тоже учитываются. Фоновая задача стирает файл и только потом убирает ключ из очереди. Повторное удаление безопасно.
- **Х-3.** Записи в очереди старше часа означают, что фоновая задача не работает.
- **Х-4.** Осиротевшие файлы (загружены в хранилище, но запись в БД не создана) на демо допускаются осознанно. Сверку хранилища с БД можно добавить позже.

## Открытые вопросы

- Формат результата генерации (`listing.result`): обсуждается отдельно. Формат бэкенда и формат контракта сейчас расходятся. В любом случае результат хранит версии площадок (Г-7).

- Открытая регистрация: кто угодно может завести аккаунт и тратить деньги на AI. Для демо неважно, решить до реальной эксплуатации.
- Поле `name`: как его задавать — при регистрации или позже в профиле. В контракте его пока нет.

- Лимит в 20 фото на объявление.
- Какое хранилище на демо (MinIO в Compose?).
